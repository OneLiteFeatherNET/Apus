# Apus Phase 3 — Hosting: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make rendered maps reachable at their own address. A `BlueMapHosting` resource creates a BlueMap webserver Deployment that reads the maps directly from S3, complete with Service, Ingress, and certificate — and reports the URL back in the status.

**Architecture:** The BlueMap CLI cleanly separates rendering from webserver operation (`-w/--webserver`). A hosting pod is the same CLI in webserver mode with the `BlueMapS3Storage` addon, which reads the finished maps from the map bucket. Unlike rendering, this pod needs an **actual configuration file**: the environment-variable contract from Phase 1 doesn't cover `webserver.conf` or the list of maps to display. This is exactly why `BlueMapConfigBuilder` was built in Phase 2a and deliberately left unwired.

**Tech Stack:** Java 25, JOSDK 5.5.1, Fabric8 7.8.0, BlueMap-CLI 5.23, JUnit Jupiter, Fabric8 Mock Server, Testcontainers.

## Global Constraints

- Java toolchain 25, base package `net.onelitefeather.apus.operator`.
- API group `bluemap.onelitefeather.net`, version `v1alpha1`. `BlueMapHosting` is **namespaced**.
- Override `initSpec()`/`initStatus()`, initialize every group in the field — a `null` spec already blocked three parallel tasks in Phase 2a. The recursive null-check test in `IngestResourceTest` shows the pattern.
- **Ownership check** by name **and** UID before every write, a conflict condition instead of taking over. That was a security finding in Phase 2a.
- **Shared `Labels` class** for all generated resources.
- `client.supports(...)` for foreign CRDs (`Certificate` from cert-manager), so a missing cert-manager doesn't cause a crash.
- Credentials never go into status, events, logs, or ConfigMaps — S3 credentials come via `secretKeyRef` from the Secret generated by Rook.
- AGPL header via Spotless, Conventional Commits, **no** Claude attribution, identifiers and Javadoc in English.

### What already exists and is to be used

- `BlueMapConfigBuilder` (Phase 2a) generates `core.conf`, `maps/<id>.conf`, and `storages/s3.conf`. Phase 3 adds `webserver.conf`, and **multiple** maps now have to appear in a single configuration.
- `Labels`, `Conditions`, `Ref`, `OperatorConfig`
- The ownership and locking pattern from `BlueMapMapReconciler` and `BlueMapRenderReconciler`
- `runner/` as a template for a container image (non-root, required variables first, `exec`)
- Verified CLI flags: `-w/--webserver` starts only the webserver, `-c <folder>` sets the configuration folder, the `packs/` folder is fixed under `<config>/packs`

### Verified cluster facts

From `Kubernetes-FLUX`: there are two IngressClasses (`nginx` and `cloudflare-tunnel`), cert-manager with a step-issuer, and Rook-Ceph as S3. The hosting pod reads from the same bucket the render writes to.

**The substantive difference from the render case:** A render pod knows exactly one map and gets its configuration from environment variables. A hosting pod displays **multiple** maps and additionally needs `webserver.conf`. Each map gets its own `maps/<id>.conf` and its own storage entry, because the maps can live in different buckets.

### Task 2: Hosting image *(parallel with Task 3)*

> Its own worktree. Only files under `hosting/`. Check the worktree base first (`git log --oneline -1`) — in earlier phases, worktrees were branched off the wrong state.

Analogous to `runner/`, but in webserver mode. The container runs **continuously**, not as a job.

**Environment variable contract:**

| Variable | Required | Meaning |
| --- | --- | --- |
| `APUS_S3_ENDPOINT` | yes | S3 endpoint |
| `APUS_S3_ACCESS_KEY` | yes | Access key |
| `APUS_S3_SECRET_KEY` | yes | Secret key |
| `APUS_S3_REGION` | no | Default `us-east-1` |
| `APUS_WEBSERVER_PORT` | no | Default `8100` |

Here, the map and storage configuration arrives **as a mounted ConfigMap** — unlike rendering, where environment variables suffice. The entrypoint only fills in the credentials in the storage files that the operator generated without them. Watch out: a mounted ConfigMap is read-only, so the entrypoint has to copy it into a writable directory before filling anything in.

**Operationally relevant:**

- A readiness check must be possible. Check which path BlueMap's webserver serves, and document it — the reconciler in Task 4 needs it for the probes.
- `exec` for the main process, so `SIGTERM` reaches it.
- Non-root.
- Credentials must not appear on the process command line. `runner/bin/bundle-sync.sh` explains in a comment why this was solved via a configuration file in the runner.

**Verification:** Build the image, start it against a MinIO with a previously rendered map, and prove with an HTTP call that the map is served. Without this proof, the task is not considered done.

### Task 3: Kubernetes resources for hosting *(parallel with Task 2)*

> Its own worktree. Only `operator/src/main/java/.../hosting/HostingResourceBuilder.java` and its test. Check the worktree base first.

```java
public final class HostingResourceBuilder {
    public static Deployment deployment(BlueMapHosting hosting, String configMapName,
                                        String bucketSecretName, OperatorConfig config);
    public static Service service(BlueMapHosting hosting);
    public static Ingress ingress(BlueMapHosting hosting);
    /** @return empty when TLS is disabled */
    public static Optional<Certificate> certificate(BlueMapHosting hosting);
}
```

**Tests that matter:**

- All generated resources carry the shared `Labels` and an `ownerReference` to the `BlueMapHosting`, so Kubernetes cleans them up.
- Credentials come via `secretKeyRef`, never as plaintext in the manifest.
- The Ingress points to the Service, the Service to the pods, and the Ingress carries the hostname from the spec.
- If TLS is enabled, a `Certificate` is created and the Ingress points to its Secret; if disabled, none is created.
- The Deployment mounts the configuration ConfigMap.
- Readiness and liveness probes are set. **Reason:** without a readiness probe, the Service sends requests to a pod that is still loading the maps from S3.

`Certificate` is a cert-manager resource; model it lean as its own `CustomResource`, the way it was done for the Rook types, and **not** via CRD generation.

### Task 4: `BlueMapHostingReconciler`

Generates, from a `BlueMapHosting`: ConfigMap (via `BlueMapConfigBuilder.buildForHosting`), Deployment, Service, Ingress, optionally a Certificate. Writes the URL into the status once the Ingress is ready.

**Binding:**

- Ownership check by name and UID before every write.
- The referenced maps must live in the same namespace and have a bound bucket in their status. If one is missing, no Deployment is created, only a descriptive condition — a webserver pointing at an empty bucket would just serve a broken page.
- Check `client.supports(Certificate.class)` before touching cert-manager resources.
- If the maps change, the ConfigMap must be updated **and** a pod restart triggered — BlueMap only reads its configuration at startup. The usual way is an annotation on the pod template carrying a checksum of the configuration.
- Registration in `ApusOperator`.

### Task 5: Integration test

Against k3s and MinIO: place a rendered map in MinIO (use the result from the existing render integration test, or render it within the test), create a `BlueMapHosting`, reconcile it, and prove that Deployment, Service, and Ingress are created and the ConfigMap contains the expected map files.

The full network path through a real Ingress controller is expensive to set up on k3s; instead, prove that the hosting pod itself serves the map (Task 2 already covers this) and that the generated Kubernetes resources fit together. Note in the report what this does **not** cover.

Its own `integrationTest` task, not part of `build`.
